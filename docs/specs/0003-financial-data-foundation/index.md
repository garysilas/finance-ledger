# 0003. Financial data foundation

**Date**: 2026-11-12
**Status**: Proposed

## Summary

Store financial records with exact amounts, clear ownership, and explainable spending rules. Keep imported facts separate from owner corrections. Encrypt provider tokens with a key outside the database and repository. Build internal services now, without financial screens, sign in, or provider requests.

## Requirements

As the owner, I want durable records and trustworthy spending rules before connecting accounts or setting budgets.

1. **AC-1**: Reviewed, explicitly applied migrations create owner, connection, account, transaction, category, budget, audit, and request receipt records. Database constraints enforce identity and owner consistency. Restart retains data. The application role cannot change schemas.
2. **AC-2**: Money uses signed bigint minor units and an explicit currency scale. USD uses cents. Decimal input converts exactly or fails without rounding. Supported foreign currencies remain stored but never enter USD totals. Unsupported currencies or precision fail without cursor advancement.
3. **AC-3**: Spending uses provider posted calendar dates. America/New_York defines current months and timestamp boundaries, including daylight saving changes. The zone locks once financial data exists. Refunds reduce their effective category in their posted month. Transfers and card payments never count as spending.
4. **AC-4**: Provider categories and classifications remain separate from independent owner overrides. Overrides survive sync and can be reset. Unknown outflows count as Uncategorized spending. Unknown inflows do not reduce spending. Archived categories retain history. Uncategorized remains active.
5. **AC-5**: Pending outflows and refunds remain separate from posted spending and budgets. Explicit pending replacement links preserve overrides without replacing explicit posted overrides. Removed and replaced records remain stored but do not count. Amount and date matching never merges transactions.
6. **AC-6**: Connection and provider transaction ID identify imports. A batch and its cursor commit atomically. Repeated delivery cannot duplicate records or audit effects. Stale cursors and ambiguous replacement links fail. Concurrent imports cannot erase owner corrections.
7. **AC-7**: Owner, category, and month have at most one nonnegative USD budget. Zero and no budget are distinct. Refunds can make spending negative. There is no rollover. Stale owner writes return a conflict.
8. **AC-8**: Tokens use AES 256 GCM authenticated encryption, fresh nonces, record binding, and a versioned envelope. An owner private key file outside the repository is required only for token operations. Missing or incorrect keys block token operations, not historical reads. Secrets and financial payloads never enter logs, browser output, or model context.
9. **AC-9**: Disconnect retains history. Final local disconnect clears token material and prevents imports. Provider revocation and reconnect remain later work. Recovery requires the matching key backup or explicit reconnect, never silent key replacement.
10. **AC-10**: Monthly results include exact category and posted totals, separate pending buckets, exclusion counts, and connection freshness. Missing balances never become zero. Foreign currencies and missing balances reduce coverage. A cursor never proves complete history.
11. **AC-11**: Successful service mutations write durable request receipts atomically. Changed records also produce minimal audit events; no ops do not invent revision changes. Retries duplicate neither receipts nor events. Audit stores operation metadata, not financial values or secrets. No unauthenticated route exposes financial services.
12. **AC-12**: Isolated database checks prove migrations, constraints, rollback, retries, concurrency, and totals. Vitest covers pure rules and crypto. Warm monthly reads over 100000 synthetic transactions meet a 500 millisecond target. Production builds still need no database or secrets.

## Decision

**Chosen option**: A relational foundation with narrow internal services, integer money, separate overrides, and encrypted token envelopes. Retain Drizzle, pg, Postgres 18, Node, and Zod. Introduce Drizzle Kit for reviewed SQL generation and explicit migration application. No crypto package, provider SDK, auth package, public endpoint, or UI is needed.

**Implementation skills**: No additional community skill informed the decision. Optional migration skill and MCP discovery was deferred. Follow installed package documentation and existing project boundaries during implementation.

This spec governs scope feature 3. Confirmation ratifies content, not shipment. Status follows the feature lifecycle.

## Feature design

### Records and relationships

Use the `ledger` schema. Internal IDs are UUIDs generated by Node crypto, independent of provider IDs. Fields are required unless marked optional. All records have database supplied `created_at`. Mutable records also have `updated_at` and bigint `revision`, initially 1. Serialize bigint as decimal strings, calendar dates as YYYY-MM-DD, and instants as UTC ISO 8601.

| Record | Fields | Constraints |
| :--- | :--- | :--- |
| owner | id, singleton flag fixed true, time_zone, timestamps | Unique singleton flag. Explicit initialization creates one owner. Zone is America/New_York. No sign in fields. |
| connection | id, owner_id, provider, environment, provider_item_id, optional institution_id and institution_name, state, optional token envelope, optional sync_cursor, optional last_successful_sync_at, revision, timestamps | Owner has many connections. Provider is plaid, environment is sandbox. Unique provider, environment, provider_item_id. |
| account | id, owner_id, connection_id, provider_account_id, name, optional official_name, type, optional subtype, optional currency and scale, optional current_units, available_units, credit_limit_units, balance_observed_at, archived_at, revision, timestamps | Connection has many accounts. Unique connection_id and provider_account_id. Currency and scale are present together. Amounts require both. |
| transaction | id, owner_id, connection_id, account_id, provider_transaction_id, amount_units, currency_code, currency_scale, posting_state, provider_date, optional posted_date and authorized_date, optional removed_at, superseded_by_id, provider_pending_transaction_id, description, optional merchant_name and provider_category_code, provider_category_id, provider_classification, optional owner_category_id and owner_classification, category_intent, classification_intent, optional category_inherited_from_id and classification_inherited_from_id, owner_edit_revision, revision, timestamps | Account has many transactions. Unique connection_id and provider_transaction_id. Posted state requires posted_date. Pending state has no posted_date. |
| category | id, owner_id, stable_key, label, optional archived_at, revision, timestamps | Unique owner_id and stable_key. Categories belong to one owner. |
| budget | id, owner_id, category_id, month, limit_units, currency_code fixed USD, revision, timestamps | Unique owner_id, category_id, month. Month is a date on day 1. Limit is nonnegative. |
| audit | id, owner_id, receipt_id, actor_type, operation, target_type, target_id, resulting_revision, created_at | Append only, with a unique event ID. Actor is owner, provider, or setup. Reference the matching owner and receipt. No uniqueness rule on target revision. No amounts, descriptions, cursor, or token fields. |
| request_receipt | id, owner_id, operation, request_id, request_digest, target_id, resulting_revision, outcome, operation_counts, optional committed_cursor, correction_conflicts, created_at | Unique owner_id, operation, request_id. Immutable after commit. Counts contain inserted, updated, and removed counts. Correction conflicts contain record IDs, field names, and safe reason codes only. Cursor is private sync state, never diagnostic data. |

Use composite foreign keys to enforce matching owner and connection on account and transaction references. Categories and budgets enforce matching owner. A transaction's supersession target must belong to the same owner, connection, and account. Prevent self links and multiple predecessors claiming the same posted record. Deletion uses RESTRICT for financial relationships. The application role has no financial DELETE permission and no audit or receipt UPDATE or DELETE permission.

The six financial records remain the confirmed model. Audit and request receipts are metadata records approved during security and review resolution. The application role may SELECT and INSERT receipts, but never UPDATE or DELETE them. Receipts remain durable for the lifetime of retained financial data; no pruning is introduced.

### Categories and classification

Seed stable keys for Housing, Utilities, Groceries, Dining, Transport, Health, Shopping, Entertainment, Travel, Personal care, Fees, Other, and Uncategorized. Seed keys use lowercase words with underscores. Setup is repeatable and never resets an existing label or archive state. No category management UI is included.

Classification values are `spending`, `refund`, `income`, `transfer`, `card_payment`, and `unclassified`. Effective category and classification use the owner override when present, otherwise the imported value. Each field has its own intent state: `untouched`, `override`, `reset`, or `inherited`. An explicit nonnull owner edit sets override. An explicit null sets reset, follows the provider, and blocks later pending inheritance. An omitted edit field makes no change. Untouched and reset require null overrides; override and inherited require nonnull overrides. Inherited fields also name their source pending record through an ownership checked reference. Any missing imported category, including a refund's category, resolves to Uncategorized. Unknown positive outflows fall back to spending and Uncategorized. Unknown negative inflows stay unclassified. Zero values contribute zero.

Provider classification and category mapping are supplied as validated normalized inputs by the future provider adapter. The foundation stores the original provider code but does not guess Plaid code meanings or install an adapter. Tests use explicit synthetic classifications. Feature 5 must specify and test the real mapping before importing provider data. Missing mapping always uses the fallbacks above.

Spending classifications require nonnegative amounts. Refund and income classifications require nonpositive amounts. Transfer, card payment, and unclassified may have either sign. Reject contradictory explicit classifications instead of silently changing signs. Category and classification edits are independent, but the resulting classification must satisfy this sign rule.

Archive preserves existing links and totals. Reject new assignments and budget creation against archived categories. Existing budgets remain readable and editable. Existing provider assignments to archived categories remain stable, but new imports map such categories to Uncategorized. Uncategorized cannot be archived. Category deletion and split transactions are outside scope.

### Exact money and dates

Positive transaction amounts mean outflow, negative amounts mean inflow. Account balances retain provider signs and types, not transaction signs. Positive credit card and loan balances mean debt. Later net worth subtracts liabilities from assets; this foundation does not publish a net worth service.

Use a checked in currency scale registry, keyed by ISO currency code, with a recorded edition. Copy and review the scale data during implementation rather than adding a money library. Each stored amount carries its scale. USD scale is 2. Unknown codes, unofficial codes, excess precision, nonfinite values, and bigint overflow return `UNSUPPORTED_MONEY` or `INVALID_INPUT`. Never round. Inputs are decimal strings, not JavaScript numbers. Future provider adapters must preserve decimal precision before calling the foundation. No foreign exchange conversion is provided.

A currency scale change requires an explicit migration, not reinterpretation of stored units. Validate amount and scale in services and use database checks for registry consistency and bigint range. Aggregate with exact Postgres numeric sums or bigint arithmetic, never a float. Totals may exceed one row's bigint range and therefore serialize as unrestricted integer strings.

Accept only valid Gregorian calendar dates within years 0001 through 9999, with exact YYYY-MM-DD spelling, and months with exact YYYY-MM spelling in that range. Reject invalid days, non leap February 29, timestamp strings in date fields, and arithmetic overflow. For December 9999, use an inclusive final date predicate rather than creating an out of range next month. Do not use JavaScript date rollover to validate input. Provider posted dates are calendar dates and are never shifted through UTC. Preserve `provider_date` for pending records separately from optional authorization date. Posted monthly reads filter `posted_date >= month_start` and `< next_month_start`. Pending buckets use `provider_date` for month membership and are labelled provisional in their contract. Explicit requested months are YYYY-MM; omitted month comes from an injected server clock interpreted in owner.time_zone. Lock zone changes at the database boundary once a connection, category, or budget exists.

### Lifecycle and atomic imports

Connections use `active`, `needs_reconnect`, and `disconnected`. Creation requires an encrypted token and starts active. Active and needs_reconnect require an envelope. Disconnected requires no envelope. Only active permits imports and provider token decryption. Receipt lookup may acknowledge an earlier committed operation in any current state without replaying it.

| Current state | Requested state | Result |
| :--- | :--- | :--- |
| active | needs_reconnect | Retain envelope and history, stop imports. Source is an explicit trusted provider failure result. |
| active or needs_reconnect | disconnected | Clear envelope without loading the key or decrypting. Retain cursor, records, and history. |
| any state | same state | Successful no op, subject to request receipt and revision rules. |
| needs_reconnect | active | INVALID_TRANSITION, recovery and token replacement are deferred. |
| disconnected | active or needs_reconnect | INVALID_TRANSITION, reconnect reconciliation is deferred. |

The local disconnect service makes no provider request and does not claim token revocation. A later flow must explicitly report provider revocation outcome separately from local disconnection, including when key loss prevents provider access. No general target state operation replaces a token.

Transactions have independent pending or posted state, removal marker, and supersession link. Active records have neither removal nor supersession. Repeated removal is a no op. A later explicit upsert may restore a removed record when the provider presents it as current. A superseded pending record stays excluded. Imports never clear explicit owner overrides or reset intent. The inherited classification exception below is reported, not silent.

A provider batch accepts an expected cursor, next cursor, account observations, transaction upserts, removal IDs, and a stable request UUID. Limit each batch to 1000 total record operations and 2 MiB of validated input. A provider sync run can stage multiple pages before calling this service; provider pagination and mutation retry protocols belong to feature 6. Do not imply one provider page is a complete sync.

Reject duplicate account observation IDs, duplicate transaction upsert IDs, duplicate removal IDs, and any transaction identity present in both upserts and removals. Reject attempts to change an existing transaction's account or connection. After validating the batch, lock the connection row and look up the durable request receipt before checking current state or cursor. A matching receipt returns already applied even after later batches commit. Otherwise require active state and the exact expected cursor, including explicit null comparison. Lock affected transactions in stable ID order. Apply account observations, transaction upserts, explicit replacement links, then removals. Advance the cursor, insert the receipt, and append audit events in the same transaction. A failure rolls everything back.

Pending links may arrive out of order. Retain the provider pending ID on the posted record and reconcile when either side arrives. Only explicit links within the same account may match. A link can be filled from null once; after establishment, reject changes or clearing the provider pending ID, supersession target, or a linked record's posting state. Reject ambiguous links, account mismatches, and cycles. A restored pending record may also become superseded in the link phase and remains excluded. Removing a posted successor never reactivates its predecessor. Missing removal IDs are successful no ops. Unlinked pending records remain pending until explicitly removed; do not invent a timeout or match.

Copy each pending override only into an untouched posted field. Explicit posted resets and overrides always win. A copied field records inherited intent and its pending source ID. Reject new owner edits to superseded pending records with CONFLICT and successor ID so callers can edit the posted record instead. If inherited classification contradicts the posted sign, keep the posted provider classification and leave that field untouched, reporting a correction conflict in the receipt and batch result. If a later provider amount change invalidates an inherited classification, clear only that inherited classification and its source reference, include the previous source ID in the reported conflict, and restore untouched intent. An incompatible explicit posted override blocks the batch with INVALID_INPUT until corrected. Provider category changes never clear owner intent. Increment owner_edit_revision whenever inheritance changes an effective owner field.

### Token envelope and recovery

Use Node crypto AES 256 GCM, a random 32 byte key, fresh random 12 byte nonce, and 16 byte authentication tag. Envelope fields are version 1, key ID, nonce, ciphertext, and tag. Store binary fields as bytea. The entire group is present or absent. Build additional authenticated data from a deterministic encoding of version, key ID, owner ID, connection ID, provider, and environment. Changing any bound value must fail authentication.

The configured key file is an absolute path outside the repository, a regular file owned by the current user, with mode 0600. Reject symbolic links and any group or other permission. File content is one canonical base64 encoded 32 byte key, with at most one trailing newline. Key ID is an explicit nonsecret configuration value. Do not derive it from a password. Validate lazily for token operations. Never log file paths, envelope values, plaintext, or crypto exceptions.

No key is generated during startup, migration, or an error path. The later setup instructions must give an explicit owner initiated key creation procedure that refuses to overwrite an existing file. Keep a secure separate backup of the key and its ID. Database backups contain encrypted tokens, not their key. Restore requires both. Without the key, keep history and use a later explicit provider reconnect. Unknown format versions and key IDs fail closed. Bulk rotation is deferred; version fields make it possible later.

### Internal service surface

Runtime database and crypto modules import `server-only`. Pure money and classification rules may remain separate from runtime dependencies. Services live in `src/features/finance/`; persistence and key loading live in `src/server/`. Every operation accepts an explicit owner ID, except initial owner creation. This is ownership scoping, not authentication. No route or Server Action exposes these operations until feature 5 supplies an authenticated owner context.

| Service | Inputs | Outputs | Important errors |
| :--- | :--- | :--- | :--- |
| initializeOwner | requested UUID, zone fixed America/New_York, request UUID | owner ID, seeded category IDs; repeat setup returns existing owner | CONFLICT, CONFIG_INVALID |
| createConnection | owner ID, provider item and institution fields, token plaintext from trusted adapter, request UUID | connection ID and state, never token | INVALID_INPUT, KEY_UNAVAILABLE, CONFLICT |
| applyProviderBatch | owner ID, connection ID, expected and next cursor, normalized records, request UUID | applied or already applied, original committed cursor, safe counts, correction conflicts | CONFLICT, UNSUPPORTED_MONEY, INVALID_INPUT |
| getConnectionSyncState | owner ID, connection ID | current state, cursor, revision; trusted adapter only | NOT_FOUND, DB_UNAVAILABLE |
| setConnectionState | owner ID, connection ID, expected revision, target state, request UUID | state, revision; disconnected clears envelope | CONFLICT, INVALID_TRANSITION |
| setTransactionOverrides | owner ID, transaction ID, expected owner edit revision, independent nullable overrides, request UUID | effective classification, category ID, new edit revision | CONFLICT, INVALID_INPUT, NOT_FOUND |
| archiveCategory | owner ID, category ID, expected revision, request UUID | archived state, revision | CONFLICT, INVALID_INPUT, NOT_FOUND |
| setBudget | owner ID, category ID, month, limit in USD cent string, expected revision or create only marker, request UUID | budget ID, limit, revision | CONFLICT, INVALID_INPUT, NOT_FOUND |
| getMonthlySpending | owner ID, optional YYYY-MM month | result described below | INVALID_INPUT, NOT_FOUND, DB_UNAVAILABLE |
| decryptConnectionToken | owner ID, connection ID | plaintext only to trusted provider adapter, never a display DTO | KEY_UNAVAILABLE, TOKEN_UNREADABLE, NOT_FOUND |

These are internal functions, not HTTP endpoints. All writes validate with Zod before database work. Missing records and foreign owner references share NOT_FOUND. Bound text inputs: IDs and codes 256 characters, names 512, description 4096, cursor 8192, token 16384. Reject oversized data, never truncate provider identity. No lists or unbounded transaction exports are added. Later list services must paginate.

Owner mutations use expected revisions. Serialize all mutations sharing owner, operation, and request UUID with a transaction scoped advisory lock. Acquire this before any connection or target row lock. Imports then lock their connection. Consult request_receipt before state, cursor, or target revision checks. A matching receipt returns an already applied acknowledgement with the original target ID, revision, counts, and correction conflicts. An import acknowledgement includes that receipt's original committed cursor, never a later cursor. It is labelled historical and must not be used to rewind sync progress. The adapter must read the connection's current cursor through a separate owner scoped getConnectionSyncState service before continuing after a retry. A receipt does not promise an old financial snapshot. A reused UUID with different content returns CONFLICT. Concurrent first attempts also face the unique receipt constraint, so only one can commit.

Canonical digest encoding uses UTF 8 JSON with recursively sorted object keys. Reject unknown fields. Sort account observations and transaction upserts by provider ID and removals by provider transaction ID after rejecting duplicates. Preserve text exactly. Encode bigint values as canonical integer strings, normalize accepted decimal money to integer units and scale, and normalize negative zero to zero. Require optional imported fields as explicit nulls when absent; request validation canonicalizes omission to null for those fields. Override patch omission remains distinct from explicit null because it means no change. Include expected revision, expected cursor, next cursor, target identity, and all validated mutation values. Hash this canonical encoding with SHA 256. Generated IDs, timestamps, and nonces are excluded. Token plaintext and key material are never included. Connection creation retries compare owner, provider identity, environment, and institution fields only and never replace the existing token.

A valid mutation that changes no stored value creates a receipt with outcome no_change and the unchanged revision, but no audit change event. Exact retries create neither new receipts nor audit events. Changed targets increment their revisions and each produce an audit event with its own UUID. Category seeds and owner creation have setup events only when inserted. Provider imports update overall record revision, but not owner_edit_revision unless inheritance changes an owner field, so ordinary sync cannot cause false owner edit conflicts.

### Spending result and value sourcing

Return one consistent database snapshot. Monthly candidate transactions belong to the owner and fall within the requested month using posted_date for posted rows and provider_date for pending rows. Establish this set before applying currency, classification, removal, and supersession exclusions. Exclusion counts use that same set, not authorization dates or row update times. Balance coverage uses all nonarchived accounts belonging to the owner, including retained accounts on disconnected connections. Count missing current balances and non USD or unknown balance currencies independently; categories may overlap. Account coverage is current snapshot metadata, not a reconstruction of historical balances for the selected month. No cached aggregates or materialized totals. Posted total is the signed sum of active USD posted records whose effective classification is spending or refund. Category totals use the same rows and sum to the posted total. Refunds may produce negative categories and totals. Budget remaining equals limit minus category spending. Never clamp remaining or spending to zero. Budget status is absent, under, at_limit, or over.

Return pending outflows as a nonnegative sum and pending refunds as a nonpositive sum, separately. Apply the same currency, transfer, removal, and supersession exclusions. Include all categories with a matching budget or any qualifying amount, including archived categories. An empty month returns zero totals and an empty category list unless budgets exist.

| Value | Source |
| :--- | :--- |
| owner and zone | Explicit owner ID scoped to owner row; owner.time_zone |
| month and boundaries | Validated month argument, or injected server clock in owner zone; calendar month arithmetic |
| exact totals and units | transaction.amount_units, currency code and scale, effective classification, activity markers, date filters |
| category labels and amounts | Effective category ID joined to owner category rows; same qualifying transaction set |
| budget limit, remaining, status | Matching budget row, or explicit absence; limit minus category total |
| pending buckets | Active pending rows by provider_date and effective classification; separate signed sums |
| exclusion counts | Independent predicates on monthly candidate rows for foreign currency, unclassified inflow, transfer, card payment, removed, and superseded; counts may overlap and are not additive |
| connection freshness | Per connection state and last_successful_sync_at; null means never observed |
| balance coverage | Account currency, nullable current_units, balance_observed_at, archive state; count missing or foreign balances, no net worth total |
| history completeness | Fixed unknown value in this foundation; never inferred from cursor or earliest transaction |
| IDs and revisions | Internal generated UUIDs, database revision increments, explicit request UUID |
| token recovery outcome | Envelope version and key ID, validated key file, authenticated decryption result |
| audit time and actor | Database clock and explicit service actor: setup for initialization, provider for imports, owner for corrections and budgets |
| retry acknowledgement and historical cursor | Immutable request_receipt target, revision, committed_cursor, operation_counts, and correction_conflicts |
| current sync cursor | Current connection.sync_cursor through getConnectionSyncState, not a historical receipt |
| override inheritance eligibility | Per field intent state and ownership checked source pending record |
| correction conflict | Explicit pending source link, inherited classification, and posted amount sign; safe record IDs and reason only |

Return amount and count strings where bigint applies. No raw token, cursor, database error, or provider response is included in a spending result. Services that return a committed cursor are private to the future adapter only.

### Security, configuration, and operation

The scope is one local personal owner, Sandbox only, with no payment processing or regulatory certification claim. Keep existing loopback and server private boundaries. The foundation does not solve sign in. The unauthenticated status page remains free of financial records. Access by the same operating system user is outside the protection provided by application authentication and token encryption.

Use a dedicated migration login, distinct from bootstrap and application logins. The bootstrap login provisions it explicitly for both new and existing volumes, without deleting data or changing existing passwords silently. The migration role owns the ledger schema and tables, cannot create roles or databases, and is never loaded by the app. Grant the app only schema usage, needed financial SELECT/INSERT/UPDATE, audit SELECT/INSERT, and required sequence access. No TRUNCATE, schema creation, or migration journal write rights. Restrict PUBLIC schema rights and define grants for future objects owned by the migration role. Verify effective privileges, not just direct grants: inherited membership, SET ROLE, ownership, PUBLIC rights, journal access, and default privileges on a newly created test table. The application role must have no membership path to migration or bootstrap authority. Audit and receipt guarantees cover service mutations only. Direct SQL with application credentials can bypass service audit and must not be described as tamper proof auditing. This refines spec 0001's broad bootstrap migration permission for feature 3 only.

| Setting | Purpose |
| :--- | :--- |
| MIGRATION_DATABASE_URL | Dedicated migration connection on 127.0.0.1:5432, same configured application database. Private CLI only. No query options or fragment. |
| LEDGER_MIGRATION_USER, LEDGER_MIGRATION_PASSWORD | Explicit owner supplied login settings for provisioning; distinct credentials. Never client exposed. |
| LEDGER_TOKEN_KEY_PATH | Absolute private key file path, required only for token operations. |
| LEDGER_TOKEN_KEY_ID | Nonempty stable key identifier, maximum 64 characters, required with key path. |
| TEST_DATABASE_URL, TEST_MIGRATION_DATABASE_URL | Explicit isolated test database connections with distinct test roles and database name. Never fall back to application or migration URLs. |

Use existing identifier and loopback validation rules for new URLs. Test database identity must differ from POSTGRES_DB and use a ledger_test prefix. Test startup verifies database name and role before any writes. Follow spec 0001's separate test Compose project and volume, fixed loopback ports, sequential execution, and occupied port refusal. Do not stop owner processes or delete volumes automatically.

Add explicit generate, migrate, and database test commands during development. Generated SQL and snapshots are tracked. Review SQL before application. Migration generation and production builds need no live database or token key. Migration failures stop; use a corrective forward migration. Destructive changes need verified backup and specific approval. Initial migrations add tables and do not rewrite owner data. README changes during implementation must cover role provisioning on existing volumes, commands, key creation and backup, and safe recovery. Do not modify AGENTS.md in this design task.

Financial database operations use the existing pool limit of five, a 2500 millisecond acquisition limit, a 5 second statement timeout, and a 10 second whole operation deadline. Cancel or discard timed out work and roll back transactions. A lost commit response may have committed; return a safe unknown outcome and retry with the same request UUID. Never claim rollback without proof. No automatic retry with a new identity.

Shared service failure codes are INVALID_INPUT, UNSUPPORTED_MONEY, NOT_FOUND, CONFLICT, INVALID_TRANSITION, CONFIG_INVALID, KEY_UNAVAILABLE, TOKEN_UNREADABLE, DB_UNAVAILABLE, DB_TIMEOUT, COMMIT_UNKNOWN, and INTERNAL_FAILURE. Results contain only the code and allowlisted retry guidance, never raw errors. CONFLICT may include the successor ID for a superseded edit within the same owner. DB_TIMEOUT is used only when noncommit is known. COMMIT_UNKNOWN means acknowledgement was lost after commit may have started; retry the identical mutation with the same request UUID and inputs so its receipt resolves the outcome. Do not retry validation or key failures until corrected. DB_UNAVAILABLE and known rolled back failures may be retried with the same UUID. All service tables inherit these shared failures in addition to their listed domain errors.

Console diagnostics remain allowlisted event, outcome, and durationMs only. Use ledger.finance_operation with fixed outcome codes. No IDs, SQL, payloads, raw exceptions, or key material. Durable audit is different from diagnostics and remains private. Audit failure aborts its mutation. Test injection remains an internal dependency seam, never a request parameter.

### Critical test scenarios

1. Fresh isolated database migrates, seeds one owner and categories, stores a connection/account/transaction, reads exact monthly spending, then survives restart. App role cannot run DDL or modify audit history (AC-1, AC-11, AC-12).
2. Decimal precision, negative refunds, zero, bigint limits, aggregate overflow beyond row bigint, currency scale mismatches, and unsupported currencies never round or advance a failed cursor (AC-2, AC-6).
3. Posted dates at month boundaries, leap February, daylight saving changes, current month clock injection, and refunds posted in a later month produce exact totals (AC-3, AC-10).
4. Provider corrections, owner resets, archived categories, unknown classifications, and two concurrent owner edits preserve the specified effective values (AC-4, AC-7).
5. Pending replacement in both arrival orders, duplicate links, removed records, restored records, and posted override precedence cannot double count or lose corrections (AC-5, AC-6).
6. Failure midway through batch, stale cursor, repeated delivery, mismatched retry payload, lost commit response, and concurrent imports prove atomic behavior and audit deduplication (AC-6, AC-11).
7. No budget, zero budget, exceeded budget, refunds beyond purchases, create races, and stale edits remain distinct (AC-7, AC-10).
8. Tamper ciphertext, tag, nonce, owner, connection, provider, environment, version, and key ID. Missing or unsafe key files block tokens but not reads. Disconnect clears tokens and retains history (AC-8, AC-9).
9. Empty data, foreign currency, null balance, stale connection, and unknown history disclose coverage. Category totals reconcile with posted totals. Logs and status responses contain no private data (AC-10, AC-11).
10. Seed 100000 synthetic transactions across 24 months in the isolated database, run ANALYZE, warm five monthly reads, then measure twenty reads through the service. Require nearest rank p95 at most 500 milliseconds. Record machine, Postgres version, fixture shape, and EXPLAIN ANALYZE plan. No external calls, instrumentation payload logging, or live owner data (AC-12).

Review regression cases must also prove explicit posted resets block inheritance, category and classification intent remain independent, superseded pending edits return the successor, and incompatible inherited classifications produce correction conflicts. Reject duplicate and overlapping batch operations, changed links, and cross account identities. A removed successor must not revive its predecessor. Retry an earlier batch after a later batch commits and prove that its historical cursor cannot replace current sync state. Equivalent array orderings and decimal representations must share a digest, while override omission and null must differ. Check no op receipts, event deduplication, missing key local disconnect, unknown commit acknowledgement, uncategorized refunds, date range extremes, and coverage populations (AC-3 through AC-12).

Index owner and posted_date for monthly reads, account and provider_date for pending reads, ownership foreign keys, budget owner/month/category, and provider identity uniqueness. Add or adjust indexes only from query plans. Run pnpm check, isolated database checks, build without live settings, and existing browser regression checks. New browser financial tests are not needed because no new browser surface exists.

## Build plan

Follow Tracer Bullet. Because UI is explicitly out of scope, the thin thread ends at a real internal spending read, not a fake screen.
